# Подключение Telegram позже

До этого шага workflows полностью работают в режиме проверки и сборки артефактов.
Не включай доставку, пока каждый environment не настроен и его канал не проверен.

## Каналы и аккаунт

- Релизный канал: `@itzephir_pub`.
- Nightly: приватный канал с названием `itzephir_pub_nightly`; название не означает
  существование публичного `@username`. Для него нужен числовой ID `-100…`.
- Личный аккаунт должен иметь права администратора с возможностью публикации и
  редактирования в обоих каналах.
- Включи подписи и показ профилей авторов. Убедись, что личный профиль доступен
  среди авторов сообщения. Издатель проверяет это перед отправкой.

Используется MTProto/Telethon, а не токен бота. Получи свои `api_id` и `api_hash`
на [my.telegram.org/apps](https://my.telegram.org/apps).

Для `telegram-preview` и `telegram-release` нужны **отдельные авторизованные
StringSession**, созданные локально для того же личного аккаунта. Они являются
двумя устройствами Telegram. Не копируй сессию локального MCP в CI и не дели одну
авторизацию между параллельными машинами. Конкретную генерацию и загрузку сессий
выполним при подключении Telegram; сессии нельзя коммитить или вставлять в PR.

## GitHub Environments

В Settings → Environments создай:

| Environment | Назначение |
| --- | --- |
| `telegram-preview` | Превью постов из PR |
| `telegram-release` | Публикации и правки из `main` |

В каждом environment задай secrets:

| Secret | Значение |
| --- | --- |
| `TELEGRAM_API_ID` | Числовой ID Telegram-приложения |
| `TELEGRAM_API_HASH` | API hash приложения |
| `TELEGRAM_SESSION_STRING` | Отдельная сессия личного аккаунта для этого environment |

И environment variables:

| Variable | Значение |
| --- | --- |
| `TELEGRAM_CHAT_ID` | `@itzephir_pub` в release, числовой ID приватного nightly в preview |
| `TELEGRAM_EXPECTED_USER_ID` | Числовой ID твоего личного аккаунта, одинаковый в обоих environment |

Доступ к environment можно ограничить веткой `main`: доверенная отправка превью
тоже запускается через `workflow_run` на `main`. Саму PR-ветку добавлять к списку
разрешённых веток environment не нужно.

`GITHUB_TOKEN` выдаётся самим Actions; отдельный GitHub PAT не требуется.
У jobs доставки есть `contents: write` для реестра в `telegram-state` и нет
необходимости пушить изменения в `main`.

## Включение

1. В Settings → Secrets and variables → Actions → Variables добавь **repository
   variable** `TELEGRAM_PREVIEW_ENABLED=true`.
2. Обнови PR с черновиком и проверь, что превью пришло в nightly с правильным автором.
3. Проверь список `published` постов в `main`: первый релиз отправит все ещё не
   зарегистрированные посты с этим статусом.
4. Добавь **repository variable** `TELEGRAM_RELEASE_ENABLED=true`.
5. Запусти `Posts / Release` вручную на `main` либо влей готовый пост.

Переключатели должны находиться именно среди repository variables, поскольку
они управляют условиями запуска jobs. Отключение — удалить переменную или задать
ей `false`. Полное прекращение доступа также требует отзыва CI-сессий в Telegram
→ Настройки → Устройства.

Состояние доставки хранится в ветке `telegram-state`, в файле
`publication-state.json`. Это служебная ветка, её не нужно вливать в `main` или
удалять. Она основана на `main` первого включённого запуска, но её код никогда не
используется для исполнения workflows.

Реальная отправка пока не проверена с Telegram: отсутствуют API-данные и сессии.
Проверены локальная сборка, логика публикаций и поведение при сбоях с подменёнными
отправителем и хранилищем.
